## 1. What we are trying to achieve

### 1.1 Goal

Ship a single-page, publicly accessible wedding invitation website for **Bhavna & Sreetam** that replaces a printed card. A guest opens one URL on a phone and, without logging in, signing up, or entering a code, can answer four questions:

1. Who is getting married, and what is the occasion?
2. What functions are happening, on what date, at what time — and how long until the wedding?
3. Where is each function, and how do I get there?
4. Who are these two people? (story + photos)

Each function should also *feel* like itself. The brief asks for a scroll that
travels through the celebration — a green mehndi garden, a burst of colour for
the haldi, a lit evening for the sangeet, the ceremony at the end — each
function filling the screen and handing over to the next. §6.4 specifies that
journey.

**Section order:** Hero → Invitation message → Our Story → The event journey
(four full-page panels) → Gallery → Footer.

### 1.2 Success criteria

| # | Criterion | How it is verified |
|---|---|---|
| S1 | A guest on a 390 px-wide phone can read every date, time and venue without horizontal scrolling or pinch-zoom | Manual check at 390×844 and 360×740 viewports |
| S2 | Tapping a venue opens that venue in the guest's native maps app | Manual check on iOS Safari and Android Chrome |
| S3 | Largest Contentful Paint ≤ 2.5 s on a simulated Slow 4G connection | Lighthouse mobile run |
| S4 | Lighthouse Accessibility score ≥ 95 | Lighthouse mobile run |
| S5 | The site is a static bundle — no server process, no database, no third-party form endpoint | `npm run build` output is HTML/CSS/JS/images only |
| S6 | The visual design matches the Mangal Sutra palette and typography in §4 | Side-by-side review against `Marriage.pdf` p.2 (moodboard) |
| S7 | The countdown advances once per second while the page is open, and two devices in different timezones display the same remaining time at the same instant | Manual check with device timezone set to `Asia/Kolkata` and `America/New_York` side by side |
| S9 | The site looks finished and intentional with **zero photographs supplied** and **zero externally-sourced assets**. Every mark on the page is either text, CSS, or SVG authored in this repository | Build from a clean checkout with an empty `gallery` array and no `hero.imageId`; the result is presentable to guests as-is |
| S8 | Every event card plays a **visually distinct** enter animation on scroll-in and a **visually distinct** exit animation on scroll-out. No two functions share a signature | Scroll the Events section end to end and back; the four animations are told apart without reference to the labels |

### 1.3 Non-goals (explicitly out of scope for v1)

The following are **not** built. They are listed so that their absence is understood as deliberate, not as an omission.

- **RSVP** — no form, no guest-response capture, no backend, no third-party form service, no WhatsApp/`tel:` RSVP shortcut.
- **Per-guest personalisation** — no guest list, no `?g=` codes, no name greeting, no per-guest function filtering.
- **Access control** — no passcode gate, no login. The URL is the only credential; anyone holding it sees everything.
- **Full-screen entry gate** — no sealed-envelope opener and no "tap to open" screen in front of the content. The guest lands directly on the invitation. Signature transitions (§6.5) are in-card elements, not gates.
- **Travel & stay** — no hotel list, no flight/transport guidance.
- **Closing "with gratitude" narrative section** — see §6.9 for what the footer does contain instead.
- **Background music** — no audio element, no autoplay, no music toggle.
- **Gift registry / blessings** — no payment links, no UPI QR, no registry.
- **Analytics, cookies, tracking** — none. The site sets no cookies and loads no analytics script.
- **Internationalisation** — single language (see §4.5); no language switcher.
- **CMS / admin UI** — content is edited by changing a source data file and redeploying.
- **WebGL / real-3D rendering** — where a signature reads as "3D" it is CSS 3D transforms on layered 2D artwork. No `three.js`, no GLTF model, no canvas renderer, no particle engine.
- **Externally-sourced creative** — no commissioned illustration, no stock imagery, no image-model renders, no purchased typefaces, no hotlinked assets. See §2.2.
- **Video assets of any kind** — no `<video>` element anywhere on the page, and no alpha-channel clip behind any signature. Every signature is CSS and SVG. Reasoning in §5.2.1.

### 2.1 Dependency policy

Runtime dependencies are **exactly two**: `react` and `react-dom`. There is no third.

No animation library. The earlier allowance for `framer-motion` is withdrawn — scroll reveals, the lightbox, the countdown and all four signatures are CSS transforms and platform APIs (`IntersectionObserver`, `setTimeout`, `Date`, `matchMedia`). Nothing in §6 or §7 needs a library, so none is carried.

Adding any third runtime dependency requires an explicit written justification against the §10 budget and against §2.2. Dev-only dependencies (Vite, TypeScript, Tailwind, ESLint, Prettier) are unrestricted — they ship nothing to the guest.

### 2.2 Self-sufficiency principle (binding)

**Every visual element on this site is produced inside this repository.** Nothing is commissioned, licensed for a fee, generated by an image model, downloaded from a stock library, or hotlinked. The project has no external creative dependency and no external runtime dependency.

This is a hard constraint, not a preference. A proposed asset that cannot be authored here is redesigned until it can be, or dropped.

**Complete asset manifest — every non-text mark the guest ever sees:**

### 4.2 Contrast rule (binding)

Measured against `ivory #F7EFE2`:

| Foreground | Ratio | Permitted use |
|---|---|---|
| `maroon` | 8.0 : 1 | Any text size — passes WCAG AA and AAA |
| `deep-red` | 6.9 : 1 | Any text size — passes WCAG AA |
| `mauli-orange` | 2.5 : 1 | **Never text.** Decoration only. |
| `antique-gold` | 1.8 : 1 | **Never text.** Decoration only. |

Signature-specific measurements, all against `maroon` body text:

| Background at peak of animation | Ratio | Verdict |
|---|---|---|
| `haldi-ink` on `haldi-turmeric` | 8.0 : 1 | Passes AAA — the Haldi panel's own pair |
| `maroon` on `haldi-turmeric` | 5.4 : 1 | Passes AA at any text size |
| `mauli-orange` at 12% over `sand-beige` (Sangeet beam peak) | 6.2 : 1 | Passes AA at any text size |

**Binding rule SG-C:** card text is `maroon` throughout every frame of every signature. Before a signature ships, its peak-opacity background must be measured against `maroon` and must reach ≥ 4.5 : 1. A signature that cannot meet this has its peak opacity reduced until it does — the text is never recoloured to accommodate an animation.

Any gold or orange element that carries meaning must be paired with a text label in `maroon` or `deep-red`. Gold is permitted for a decorative element of ≥ 3 px stroke weight that conveys no information.

### 4.4 Layout tokens

- Content column max-width: `1120 px`, centred.
- Horizontal gutter: `20 px` at < 640 px, `32 px` at ≥ 640 px, `48 px` at ≥ 1024 px. Applied once on a single wrapper; never zeroed by a `padding` shorthand.
- Vertical section rhythm: `72 px` at < 768 px, `120 px` at ≥ 768 px.
- Border radius: `4 px` for cards; ornamental arch shapes (the cusped *mehrab* arch in `Marriage.pdf` p.3) are SVG masks, not `border-radius`.
- Breakpoints: `sm 640`, `md 768`, `lg 1024`, `xl 1280`.

Primary language is **English**, with Devanagari used only for the theme title **मंगल सूत्र** and for function names where a Devanagari form is supplied in the content data. `<html lang="en">`. Any Devanagari run is wrapped in an element carrying `lang="hi"` so screen readers select the right voice.

### 4.6 Illustration system

Because every mark on the page is drawn here (§2.2), the drawing needs rules — otherwise sixty hand-authored SVG elements drift into sixty different styles. These rules are what make the artwork read as one commissioned set rather than as assorted clip art, and they are the operational meaning of "it looks great".

**Line.**

| Property | Value |
|---|---|
| Stroke weights | Exactly three: hairline `0.75px`, standard `1.5px`, emphasis `3px`. No other weight appears anywhere |
| Stroke colour | `antique-gold` for ornament, `maroon` for structure, `deep-red` for the mauli cord only |
| Line caps / joins | `round` throughout. No mitred corners — the deck's vocabulary is drawn with a brush, not a ruler |
| Fills | Ornament is **stroke-only**. The only filled shapes are the diya flame, flower centres, bulb glows and the mauli tassel |

**Opacity ladder.** Depth is built from four fixed steps, never arbitrary values: background `0.08`, mid-ground `0.18`, foreground `0.45`, focal `1.0`. Anything drawn at a fifth value is a mistake.

**Geometry.**

| Rule | Detail |
|---|---|
| Arches | Cusped *mehrab* profile traced from `Marriage.pdf` p.3 — five cusps, 2:3 width-to-height |
| Lotus | Seven petals, bilaterally symmetric, the outer pair swept down |
| Symmetry | Ornament is mirror-symmetric about its own vertical axis unless it depicts something physical (the cord, the hands, a falling petal) |
| Grid | Every artwork authored on a 24-unit grid; every coordinate a multiple of 0.5 units |
| Petal scatter | Positions are authored constants, never randomised, for the same reason as HS5 |

**Density.** Ornament occupies 20–35% of any panel's area. Below 20% the composition reads as unfinished; above 35% it competes with the text it frames. Measured as inked area over panel area.

**Coherence test (binding).** Any two authored assets placed side by side at the same scale must read as drawn by the same hand. Where a new asset fails this against the existing set, the new asset is redrawn — the existing set is not loosened to accommodate it.

**Motif vocabulary.** Drawing draws only from the deck's own elements (§3): lotus, eternal knot, kalash, peepal tree, diya, temple skyline, mauli cord, jaali lattice, hanging bell, mango-leaf *toran*. No motif is invented outside this list, and no motif is borrowed from a tradition the deck does not use.

#### 5.2.4 Why none of this is a video

A pre-rendered clip of the hand opening — or of the hero — was considered and rejected on the merits, independently of tooling. Each reason below is on its own disqualifying:

| # | Reason |
|---|---|
| 1 | **Transparency needs two encodes.** Alpha video requires HEVC-with-alpha for Safari *and* VP9-with-alpha for Chrome. Two files, two codecs, two failure modes, and no fallback where neither is supported |
| 2 | **Weight.** A 900 ms alpha clip at retina density runs to several megabytes. The whole page budget is 320 KB (§10.2). One clip would exceed the entire site by an order of magnitude |
| 3 | **It cannot be themed.** Authored SVG inherits `antique-gold` and `maroon` from CSS custom properties, so changing a token restyles every asset at once. A video's colours are baked in — a palette change (Q15) means re-rendering and re-encoding |
| 4 | **It cannot run the lifecycle.** §6.5 requires five states, an exit at 60% of the enter, mid-flight guarding (SG6) and replay on demand (SG9). A video is a fixed timeline: scrubbing backwards for the exit is unreliable across browsers, and `prefers-reduced-motion` has no static frame to fall back to without shipping a still as well |
| 5 | **It does not scale.** SVG is resolution-independent from a 320 px phone to a 2560 px display. A video is fixed-resolution and needs multiple renditions |
| 6 | **It is an external dependency.** Producing it needs a motion designer or a generative model, which §2.2 forbids outright |

Reason 6 alone settles it; reasons 1–5 mean the decision would stand even without §2.2.

### 6.3 Countdown (live)

Sits inside the hero, below `hero.cityLabel`. It counts down to `countdown.targetInstant` — the wedding ceremony start.

**The displayed value is live. It is recomputed from the system clock on every tick.** A build-time-baked number, a value written into the HTML at deploy, a hardcoded string, or any display that does not change while the guest watches is a defect, not an implementation choice.

| ID | Behaviour |
|---|---|
| K1 | Displays four units in this order: **Days · Hours · Minutes · Seconds**, each as a numeral with a unit label beneath it |
| K2 | The value advances once per second while the page is open and visible. The seconds figure visibly changes every second |
| K3 | Each tick computes `remaining = targetEpochMs − Date.now()` **from scratch**. The implementation never decrements a stored counter, never accumulates elapsed time, and never derives one tick's value from the previous tick's value. Timer drift is therefore structurally impossible |
| K4 | The next tick is scheduled to land on the next wall-clock second boundary — `1000 − (Date.now() mod 1000)` ms away — so the display flips in step with the device clock rather than drifting by the timer's own latency |
| K5 | On `visibilitychange` to `visible`, the value is recomputed and repainted **immediately**, before the next scheduled tick. Background tabs are throttled by every browser; without this the guest would see a stale number on return |
| K6 | Hours, minutes and seconds are zero-padded to two digits. Days is **not** padded and is **not** capped — a 692-day countdown renders as `692` |
| K7 | When fewer than 24 hours remain, the Days unit still renders, showing `0`. The unit is never hidden, so the layout never reflows |
| K8 | Unit labels pluralise against their own value: `1 Day` / `42 Days`, `1 Hour` / `0 Hours` |
| K9 | When `remaining ≤ 0`, the four units are replaced by `countdown.completedMessage`. The swap happens on the tick that crosses zero, without a reload. Ticking then stops and the timer is cleared |
| K10 | Where `countdown.targetInstant` is the `TBD` sentinel, the countdown renders `hero.dateLabel` as static text with no numerals and no ticking. It does **not** render zeros, does not render a broken counter, and does not throw |
| K11 | Two devices in different timezones show identical numerals at the same instant, because the target carries an explicit UTC offset and `Date.now()` is UTC-based (S7) |
| K12 | The timer is cleared when the component unmounts. No timer survives unmount; no leak accumulates across HMR reloads in development |
| K13 | **Accessibility.** The ticking numerals carry `aria-hidden="true"`. Alongside them sits a visually hidden sentence — `"42 days, 6 hours until the wedding"` — with `aria-live="off"`, refreshed at most once per minute. A screen reader must never be made to announce a value once per second |
| K14 | Under `prefers-reduced-motion: reduce`, the digits change with no flip, slide or fade transition — but **the countdown keeps ticking**. It conveys information, so it is not suppressed as decoration (M11) |
| K15 | Digit changes cause no layout shift: tabular figures or fixed-width digit containers per §4.3 |
| K16 | With JavaScript disabled, the countdown is absent and `hero.dateLabel` renders in its place (D8). No empty box and no frozen zeros are left behind |

### 6.4 The event journey (replaces the card grid)

The brief is explicit: *"Every event should cover the whole page"*, each with its
own entrance, joined by *"smooth transitions"* from one colour world to the next,
and finished *"like Apple websites showcasing iPhones"*.

So the Events section is not a list of cards. It is a **sequence of four
full-viewport panels** that a guest scrolls through, and the page changes colour
around them as they go.

| ID | Behaviour |
|---|---|
| EJ1 | Four panels, one per function, in chronological order: Mehndi, Haldi, Sangeet, Marriage. Order is computed from the dates, never authored |
| EJ2 | Each panel occupies `100svh` minimum and is a labelled region named by its own heading |

| EJ4 | The ground colour **transitions between panels** rather than cutting. A panel's ground reaches full strength when it owns the viewport and blends toward its neighbour at the seam |

| EJ6 | Panel content is centred in the viewport and never exceeds the content column, so a 2560 px screen does not stretch a line of text across a metre of glass |

## 7. Motion

| ID | Behaviour |
|---|---|
| M1 | Sections and cards fade in from `opacity: 0, translateY(24px)` to `opacity: 1, translateY(0)` over 500 ms with an ease-out curve, triggered when the element crosses 15% into the viewport |
| M2 | The M1 section reveal fires once per element. Scrolling back up and down again does not replay it. **This is the opposite of signature behaviour (SG5) and the distinction is deliberate:** the section reveal is page furniture arriving; a signature is a per-function performance that should play again whenever the guest returns to it |
| M3 | Reveals within a group (event cards, gallery thumbnails) stagger by 80 ms, capped at a 480 ms total stagger regardless of item count |
| M4 | Under `prefers-reduced-motion: reduce`, every **decorative** animation is disabled: elements render at their final state immediately, smooth scroll becomes instant, the lightbox opens and closes with no transition, and every signature renders statically in `entered` (SG10) |
| M5 | No parallax, no scroll-jacking, no scroll-linked video, no auto-advancing carousel |
| M6 | Animated properties are restricted to `opacity` and `transform`, with the single documented `stroke-dashoffset` exception in MK6 |
| M7 | A card runs its M1 reveal first; its signature enter (SG2) begins only after that reveal completes. The two never overlap |
| M8 | Signature triggers use `IntersectionObserver`, never a scroll-position listener |
| M9 | No signature loops, pulses or repeats while settled. Each plays exactly one pass per enter and one pass per exit |
| M10 | At most two signatures animate concurrently (SG12); page-wide animated node count stays ≤ 24 (SG13) |
| M11 | The live countdown is **exempt** from M4. It carries information, so it continues ticking under `prefers-reduced-motion`; only its digit **transitions** are removed (K14) |
| M12 | All observers and timers are disconnected and cleared on unmount |

## 8. Responsive and rendering behaviour

### 8.1 Viewport range

Correct rendering is required from **320 px** to **2560 px** wide. The page body never scrolls horizontally at any width in this range. Should any element need to exceed the content width, it sits in its own `overflow-x: auto` container.

At < 400 px the countdown's four units remain on one row; the digit size steps down via the §4.3 `clamp()` floor rather than wrapping to two rows.

Signature panels scale with their card and keep their fixed aspect ratio at every width. No signature is suppressed on small screens — a guest on a phone sees the same four signatures as a guest on a desktop.

### 8.2 Touch targets

Every interactive element has a hit area of ≥ 44 × 44 CSS pixels, achieved through padding rather than a minimum font size. This includes every signature replay button (SG9).

### 8.3 Colour scheme

The site is **light-only**. `prefers-color-scheme: dark` is ignored — the Mangal Sutra palette is an ivory-ground design and inverting it would break it. `<meta name="color-scheme" content="light">` is set so browsers do not auto-invert form controls or scrollbars.

### 8.4 Print

A print stylesheet renders the Hero heading block and the Events section on one A4 page: white background, `maroon` text, no images except the motif icons; header, gallery, countdown and every signature layer hidden.

## 9. Accessibility requirements

Target: **WCAG 2.1 Level AA**.

| ID | Requirement |
|---|---|
| A1 | Heading hierarchy is strictly ordered: one `<h1>` (couple names in the hero), `<h2>` per section, `<h3>` per event card and story beat. No level is skipped |
| A2 | Landmarks: `<header>`, `<main>`, `<footer>`, and `<section>` with `aria-labelledby` pointing at its own heading |
| A3 | A "Skip to content" link is the first focusable element, visually hidden until focused |
| A4 | Every focusable element shows a visible focus indicator of ≥ 2 px in `deep-red` with a ≥ 2 px offset. `outline: none` without a replacement is prohibited |
| A5 | All decorative imagery — ornaments, dividers, motif icons and every signature layer — carries `aria-hidden="true"` and an empty `alt` |
| A6 | All content imagery has a descriptive `alt` (enforced by V4) |
| A7 | The lightbox is `role="dialog" aria-modal="true"` with an accessible name, traps focus, and restores focus on close |
| A8 | Text contrast meets the §4.2 tables at **every frame** of every animation, including mid-splash and at peak beam opacity (SG-C) |
| A9 | Every interactive element is reachable and operable by keyboard alone. No pointer-only interaction exists — the swipe gesture in G8 is an addition to, never a replacement for, the Previous/Next buttons, and every signature replay (SG9) is a real `<button>` |
| A10 | Links that open a new tab announce that fact in their accessible name |
| A11 | Text reflows without loss of content at 320 px width and at 200% browser zoom |
| A12 | The countdown never produces a per-second live-region announcement (K13). This is the single most common accessibility failure in countdown implementations and is treated as a blocking defect |
| **A13** | No signature enter or exit alters the reading order, the focus order, or the accessible name of any element. A screen-reader traversal of the Events section produces identical output whether every card is `idle`, `entered`, or mid-animation |

## 10. Performance budget

### 10.1 Field targets (Lighthouse mobile, simulated Slow 4G, 4× CPU throttle)

| Metric | Budget |
|---|---|
| Largest Contentful Paint | ≤ 2.5 s |
| Cumulative Layout Shift | ≤ 0.02 |
| Interaction to Next Paint | ≤ 200 ms |
| Total Blocking Time | ≤ 150 ms |
| Lighthouse Performance | ≥ 90 |
| Lighthouse Accessibility | ≥ 95 |
| Lighthouse Best Practices | ≥ 95 |

### 10.2 Transfer budget (initial load, compressed)

Removing the hero photograph and the animation library reshapes this budget substantially. The v3 figure was 500 KB; it is now **320 KB** — of which 120 KB is optional font files, so the floor is 190 KB.

| Resource | Budget | Note |
|---|---|---|
| HTML, including the inline hero SVG | ≤ 44 KB | Hero composition ≤ 28 KB of this |
| CSS | ≤ 30 KB | Up from 28 KB: signature keyframes and the illustration tokens moved here from JS |
| JS | ≤ 116 KB | React + ReactDOM + ~12 KB of application code. No animation library (§2.1) |
| Fonts | ≤ 120 KB | **Optional.** Three OFL faces, subset. Zero when falling back to the system stack (§4.3) |
| Photographs | 0 KB | None on first paint. The hero is drawn, not photographed |
| **Total initial load** | **≤ 320 KB** | 190 KB with the system font stack |

**Below-the-fold, outside this budget:** signature assets (hand layers, backdrop, jhoomar, cord and knot), gallery images, story-beat images — all lazy-loaded per SG18.

**Where the savings came from.** Dropping the hero photograph removed 200 KB and moved the LCP element from an image to text (HA8), which is the single largest factor in S3. Dropping `framer-motion` removed roughly 40 KB of JS. The four signatures and the entire illustration set together add less than the one photograph they replaced, because SVG line art at these budgets is measured in single-digit kilobytes.

### 10.3 Runtime budget for signatures

| Constraint | Limit |
|---|---|
| Concurrent animating signatures | ≤ 2 (SG12) |
| Animated nodes per signature | ≤ 12 (SG13) |
| Animated nodes page-wide at any instant | ≤ 24 (SG13) |
| Frame rate during any signature | ≥ 55 fps sustained on a mid-range 2021 Android device |
| TBT contribution of the `mauli-knot` draw | ≤ 20 ms (MK6) |
| `will-change` lifetime | Only while `entering` or `exiting` (SG14) |

### 10.4 Third-party origins

**Zero.** No Google Fonts CDN, no analytics, no map iframe, no CDN-hosted library, no external script, no external stylesheet. Every byte is served from the site's own origin. Fonts are self-hosted. This makes the site function correctly behind restrictive networks and sets no third-party cookies.

Open Graph previews and favicons must be PNG — the one place SVG will not serve. No npm package, no `ffmpeg`, no image model, no design application.

| Command | Output |
|---|---|
| `npm run rasters` | Renders `og-image.png` (1200 × 630), `apple-touch-icon.png` (180 × 180) and `favicon.png` (32 × 32) from the hero and lotus SVGs into `public/` |

| ID | Rule |
|---|---|
| **R1** | The generated PNGs are **committed to the repository**. They are build inputs, not build outputs |
| **R2** | `npm run build` never invokes the raster script. A clean checkout therefore builds identically on Linux CI, on Windows, and on a machine with no Xcode tools — this script is the only macOS-dependent step in the project and nothing depends on it at build time (SS3) |
| **R3** | The script is re-run by hand only when the hero composition or the lotus motif changes, and the refreshed PNGs are committed in the same change |
